# CanIToolCall v0.2.0

This release adds a written contract for what a parser must do with **malformed or truncated** model output, 31 new fixtures that test it, and a fresh results snapshot judged by it. The engine pins are unchanged from 0.1, so every difference in the numbers comes from the corpus and the rules, not from the engines.

- Matrix: https://redd34.github.io/canitoolcall/
- Results snapshot behind these notes: [`results/2026-11-15/`](https://github.com/redd34/canitoolcall/tree/main/results/2026-11-15), with every failing case triaged in `triage.jsonl`
- Full list of changes: [CHANGELOG.md](https://github.com/redd34/canitoolcall/blob/main/CHANGELOG.md#020---2026-11-15)

## The recovery contract

[`docs/formats/recovery.md`](https://github.com/redd34/canitoolcall/blob/main/docs/formats/recovery.md) (issue #36) gives the order of outcomes a client cares about: the call the model meant, then a clean rejection, then (always a fail) a call with the wrong arguments. It sets four rules:

1. **Missing inner close, generation finished:** when the call's extent is unambiguous, recover the value. A clean rejection is a fail, but a lesser one than a corrupted value.
2. **Cut by `max_tokens`:** never return the unfinished call. A call closed by its own end marker is complete and must be kept, even when the list or section around it never closes, and the cut tail after it is not content.
3. **Streaming vs non-streaming:** calls and exceptions must match in every mode. On `expected_error` fixtures, a difference only in recovered text is `soft_pass`.
4. **Exceptions** raised by a parser are parse outcomes, never `error`.

Rule 3 changed two checks (`stream_equals_nonstream`, `split_invariance`). It predicted 16 cells would move from `fail` to `soft_pass`. The new snapshot confirms 15 of them. The 16th fixture was relabelled under rule 2.

## Fixtures and spec

- **Fixture spec 0.2.** Optional `assumes` and `finish` fields (#9, PR #38) record replay assumptions and how a generation ended. Readers accept any `0.x`, so 0.1 fixtures still validate. canitoolcall 0.1.x rejects the 0.2 corpus, so upgrade to read it.
- **500 fixtures** (469 in 0.1). 31 are derived cuts at structural boundaries, across all nine families (PR #42). `llama/l4-truncated-missing-close-bracket` now expects its first call (PR #43).

## Results (snapshot 2026-11-15, Linux x86_64, offline replay)

| Engine | Version | Fixtures it supports | Pass | Soft pass | Fail | Engine bugs found | Known upstream, still reproducing |
|---|---|---:|---:|---:|---:|---:|---:|
| vLLM | 0.30.0 | 498 | 270 | 93 | 135 | 10 | 6 |
| SGLang | 0.5.20 | 476 | 200 | 70 | 206 | 11 | 0 |
| llama.cpp | `a25c9865` | 464 | 287 | 53 | 124 | 6 | 1 |
| Ollama | `7af39318` | 273 | 234 | 13 | 26 | 4 | 3 |
| HF transformers | 5.17.0 | 51 | 34 | 7 | 10 | 3 | 0 |

Engines support different subsets of the fixtures, so these numbers are **not a ranking**. A finding is one root cause, often across many fixtures. The new findings are:
- engines that drop a complete call when output is cut after it;
- engines that corrupt or reject a value whose inner close is missing;
- parsers that raise on fixtures that do not accept an exception.

No vLLM case is untriaged. 28 older cases remain `untriaged_discrepancy` (SGLang 14, llama.cpp 7, Ollama 6, transformers 1).

## Upgrading

```sh
uvx canitoolcall@0.2.0 --version
```

Fixture files you wrote for 0.1 still validate. To use `assumes` or `finish`, set `spec_version` to `"0.2"`.
